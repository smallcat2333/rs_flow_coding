## 1. 需求

### 1.1 背景
现有图和 Feat 均可绑定唯一主会话。flowctl 已有 peers/send，但未运行的接收方不能接单，消息没有任务状态及可验证结果，也没有明确的模块代码职责。用户希望交叉需求由 Agent 互相协调，每个负责人处理自己的部分。

### 1.2 目标
- 图主 Agent 声明业务职责与负责的目录/文件；Feat 主 Agent 向对应模块派发请求并汇总验收。
- 支持按稳定会话 ID、唯一名称或流程图路径定位负责人；歧义、未知名称及无效图路径明确报错，有效 B 图从未绑定 Agent 时自动创建唯一图主，APP 与工作目录按 B 图所属目录推导。
- 请求携带目标、接口约定、验收条件和来源 Feat/任务；按模块串行处理并保存状态及结果。
- 未运行的启用会话后台续接，不切换窗口；收纳/归档负责人先等待实际用户 YES/NO 确认，YES 按原来源唯一性和手动启用规则恢复后继续原请求，NO/取消保持停用并反馈请求方。确认在后台等待、同负责人只弹一次，不接受 Agent 代答；恢复冲突或启动失败明确受阻，不无限重启。
- 复用现有 TCP、PTY、hooks、活动记录及配置，不新增聊天窗口，不复制完整会话历史；职责是协作协议，不声称提供覆盖任意 Bash 写入的安全沙箱。

### 1.3 验收标准
- [x] 能识别图主负责人和已声明职责；名称/ID前缀歧义、未知图和重叠职责不随机路由。
- [ ] 发给未运行会话的请求自动启动原会话并等待就绪；忙碌/权限等待时排队；同一模块不并发处理多个协作请求。
- [ ] 接单、处理中、完成、受阻可查询；完成必须提供结果与验证说明，非接收方不能代报；结果回到请求方并可续接它。
- [x] 收纳/归档、启动失败、进程退出及未回报的任务不会被当成完成；结果通知不产生自动相互回复循环。
- [ ] 请求、职责和结果持久化；重启后已投递但未确认的任务标受阻，避免自动重复执行；原 send、终端及会话管理保留。
- [x] 有效 B 图从无到有自动创建唯一图主，并发同图请求复用该负责人；工作目录/APP 绑定 B，未知名称和无效图不自动创建。
- [ ] 收纳与归档分别覆盖实际用户 YES/NO：YES 恢复后继续原请求并遵守忙碌队列，NO/取消维持停用并反馈；来源恢复冲突不绕过，同负责人等待不重复弹窗，Agent 不能代答。

### 1.4 初步路线
复用 agent.rs 的来源唯一性、会话续接、flowctl TCP、hooks 与活动通知。新增独立 agent_collab.rs，按任务和结果通知保存待投递队列；后台调度在接收方空闲且无正在处理的请求时送入 PTY。CLI 新增 scope/request/requests/reply，并扩展 peers 返回身份及职责。职责声明、任务状态及结果采用本地原子写入。

按推进授权由 Agent 决定常规实现细节：已有图主即负责人，不额外创造角色；明确状态控制串行处理，完成由显式回报确认；模块目录重叠须先指定单一负责人。当前工程未建立 docs/flow，相关流程图为无，本次不新建图。目标和边界已确认，无 UI 重设计，连续推进实现与自验。

**影响的流程图**：无（已扫描 docs，无既有业务图）。

## 2. 原型（活文档：UI 设计贯穿始终，随 dev 演进）

### 2.1 设计总纲
复用终端和现有协作活动记录；停用负责人的启用确认采用项目已有的 Windows 原生消息框风格，不改 Agent 页面布局。

### 2.2 控件清单
原生“重新启用 Agent”消息框：负责人、停用原因、请求来源、目标及模块；“是（YES）”/“否（NO）”，默认 NO。

### 2.3 交互说明
Agent 使用 flowctl 声明职责、发现负责人、提出任务和回报。普通使用者仍向当前 Feat Agent 提需求。后台唤醒不抢页签；受阻原因及结果通过请求查询和现有活动记录可见。

负责人收纳/归档时，原请求持久化为 awaiting_approval，由后台线程显示一次原生用户确认。YES 先校验原来源没有新负责人占用，再按手动启用规则恢复原会话并回原队列；NO/取消保持停用且原请求受阻并通知来源。等待时不持有会话/协作锁、不阻塞 IPC，后续同负责人请求共用本次确认；无面向 Agent 的同意接口。应用退出/重启使未完成确认进入受阻，原请求正文保留，不自动重弹或重执行。

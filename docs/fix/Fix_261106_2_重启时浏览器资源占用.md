# Fix_261106_2 重启时浏览器资源占用

> 状态：待观察
> 应用：flow_coding
> 创建：2026-11-06　　关闭：-

## 1. 现象
### 1.1 问题描述
用户提供启动错误截图：Tauri `app.rs:1444` 报 `Failed to setup app: runtime error: failed to create webview: WebView2 error: WindowsError HRESULT(0x800700AA)`，中文为“请求的资源在使用中”。预期恢复普通运行实例，实际只有标题为 Flow Coding 的系统错误弹窗。

### 1.2 复现步骤
1. 本会话统一编译 0.2.28，并以调试端口 9224 启动发布程序，原生主窗口与 Agent 窗口正常。
2. 核验脚本关闭该实例，等待应用进程退出后，移除调试浏览器参数立即启动普通实例。
3. 普通实例未出现预期带版本号的主窗口，脚本等待 35 秒后超时；用户随后提供上述系统错误弹窗。
4. 在确认没有本应用或关联 WebView2 残留进程后，进行一次同版本、同数据目录的普通冷启动：成功，不能稳定复现截图错误。

### 1.3 影响范围
该次应用启动失败，无法进入主窗口；现有记录没有显示图纸或 Feat 内容损坏。

## 2. 根因分析
- 已确认：错误来自 Tauri 原生 WebView2 创建阶段，先于页面内 Agent 服务读取；不是此前 `Agent 服务未初始化` 的同一错误。
- `src-tauri/src/lib.rs` 的 panic hook 通过 `MessageBoxW` 显示异常，标题固定为 `Flow Coding`。本会话曾把该消息框误认成普通主窗口，导致“已恢复普通运行”的判断错误；已撤回核验脚本中仅凭这个通用标题接受窗口的改动。
- 发生前，核验脚本使用同一默认 WebView2 数据目录，从带 `--remote-debugging-port=9224` 的实例切换到不带该参数的实例；仅等待父应用进程退出，没有验证浏览器子进程及数据目录资源已释放。
- 实际 WebView2 数据目录：`C:\Users\kaizhong_liu\AppData\Local\com.smallcat.rs-flow-coding\EBWebView`；业务数据目录另为 `%APPDATA%\rs_flow_coding`。
- 用户关闭错误提示后的进程检查：没有 Flow Coding 进程，也没有数据目录匹配本应用的 WebView2 进程，无法从当前快照追溯报错瞬间的具体占用者。
- 微软 `CreateCoreWebView2EnvironmentWithOptions` 文档将共享进程的参数不一致列为 `ERROR_INVALID_STATE`，并没有把截图的 `0x800700AA / ERROR_BUSY` 直接归因于参数不一致，因此不能据调试参数切换认定根因。参考：https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/webview2-idl#createcorewebview2environmentwithoptions
- 2026-11-06 一次普通冷启动成功：PID 73836，真实主窗口标题 `Flow Coding V.0.2.28`，原生类名 `Tauri Window`，无系统错误对话框、无窗口挂起；证明当前不再持续占用，但不证明此前具体占用源。
- 无业务流程图；本次先做启动基础设施只读诊断，不补画业务图。

**根因**：已确认 WebView2 因资源忙拒绝创建，具体资源和占用者尚未确认。
**确信度**：这是猜测：快速重启后旧 WebView2 尚未释放同一数据目录，或调试/普通启动环境切换产生瞬时冲突；当前证据不足以确定是哪一种，暂不修改产品源码。

## 3. 修复方案
- 暂不修改产品源码，不清理或重建 WebView2 数据目录，不终止其他应用的浏览器进程。
- 已纠正本机会话 `.cache` 核验脚本：错误消息框不能作为主窗口成功启动的证据；仍须匹配预期主窗口标题和应用进程。
- 原定统一重启先暂停排查；一次普通冷启动已恢复 0.2.28，未修改产品代码，后续具体修复需有稳定复现或更多现场证据。

# Fix_261106_4 API 错误仍显示运行中

> 状态：已验证待确认
> 应用：flow_coding
> 创建：2026-11-06　　关闭：-

## 1. 现象
### 1.1 问题描述
Agent 终端出现 `API error · Retrying in 0s · attempt 1/10` 时，会话列表、页签和总览仍显示「运行中」或绿色执行状态，用户无法从列表看出本轮已因接口错误中断。预期应明确显示 API 错误及原因。

### 1.2 复现步骤
1. 在 Agent 会话中触发一次模型请求，使代理返回 504 或其它接口错误。
2. CLI 在终端输出 API 错误并在原地重试；进程保持运行，回合未结束。
3. 观察左侧会话列表、顶部页签与总览：状态仍为「运行中」。

### 1.3 影响范围
仅影响 Flow Coding 对会话状态的显示；终端内容、Hook 数据、进程与协作不受影响。

## 2. 根因分析
- 后端状态只由 Hook 驱动：`UserPromptSubmit`/`PreToolUse` 置为 run，`Stop` 置为 idle，进程退出才置为 err。
- API 错误由 CLI 自行重试，既不触发 `Stop`，也不结束进程，因此 `live.status` 始终停在 run。
- 终端输出虽然已经包含错误文本并写入缓冲区，但后端从未解析它，前端只能依据 `status` 显示。

**根因**：状态机只认 Hook，缺少对 CLI 终端 API 错误输出的识别，重试期间被误判为正常执行。
**确信度**：已定位到根本原因。

## 3. 修复方案
- 后端用流式解析器跨读取块保留 ANSI 和当前行，识别行首 `API error` 与 `Connection refused` 等明确重试文本，保存 `live.api_error` 并置状态 `apierr`；工具输出和待命回放不参与识别。
- 接入官方 `StopFailure`，使用 `last_assistant_message` / `error_details` / `error` 保留最终失败原因；不标记正常完成、不投递下一条协作任务。
- 恢复：仅新回合、主会话工具调用、正常结束或 SessionStart 清除错误；键盘输入、普通通知、子代理结束均不能证明恢复。重新启动时清除旧错误，进程退出仍按 err/off 显示。
- 前端新增 `apierr` 状态：列表、页签、总览、机器人显示「API 错误」并使用告警色；文案在悬停提示中显示。
- 流程图：无（项目未建立 docs/flow 业务图，本次为内部状态识别）。
- 实现与自验已完成，待统一编译后的原生程序验收和用户确认；不提交。
